# Architecture reference

Depth-on-demand companion to `CLAUDE.md`. **`CLAUDE.md` is the lean map that loads into every
session; this file is the detail you pull when you actually touch a subsystem.** If you are adding a
capability, read the matching section here first — but do not copy it back into `CLAUDE.md`.

Source of truth beats this document wherever they disagree: the running schema is `src/migrate.ts`,
the SW cache version is `public/sw.js`, the endpoint list is `docs/API.md`, the tool list is
`docs/MCP-TOOLS.md` (both generated by `npm run docs:index`), and per-round history is
`docs/ARCHITECTURE-HISTORY.md`.

---

## The repo layer (`src/repo.ts` and `src/repo/*`)

`src/repo.ts` is a thin **barrel** re-exporting the domain modules under `src/repo/`: `exercises`,
`plan`, `sessions`, `profile`, `activities`, `memory`, `nutrition`, `fuel-state`, `chat`, `settings`,
`health`, `coach`, `propagation`, `evidence`, `intelligence`, the training-intelligence + brain
modules (`standing`, `performance`, `program-state`, `progression`, `program-blocks`,
`exercise-canon`, `marker-canon`, `training-read`, `reaction-model`, `trajectory`, `run-progression`,
`dexa-targeting`, `muscle-trajectory`, `coaching-focus`), the Era-2 daily-driver modules
(`today-agenda`, `since-last`, `goal-checkin`, `learned-timeline`), and `shared`. External code keeps
importing everything from `./repo.js` unchanged.

### Training

- Plan/sessions/sets; plan editing (`savePlanDay`/`deletePlanDay`/`replacePlan`); session-by-date
  lookup (`getSessionByDate`) and last-set prefill (`getLastSet`); session finish + summary
  (`finishSession`/`sessionSummary`).
- Epley est-1RM (`getProgress`) and PR detection (in `logSetByName`, returns `pr`/`est_1rm` — for
  `mode:'timed'` exercises a PR is a new max `duration_sec` and `est_1rm` stays null).
- Exercise CRUD (`listExercises`/`upsertExercise`/`updateExercise` — `mode` is `'reps'` or
  `'timed'`), the exercise guide (`getExerciseDetail`), volume-by-muscle (`getVolumeByMuscle`),
  training calendar (`getTrainingCalendar`).
- Weekly dashboard (`getWeeklyStats` → `{ week_sessions, week_tonnage, week_sets, streak }` plus the
  compass fields `{ week_done, week_planned, trend_lb_wk, needed_lb_wk, pace_status, weight_lb,
  goal_weight_lb, goal_date }`). `week_done` is distinct training days since Monday vs `week_planned`
  plan days; `trend_lb_wk` is a least-squares slope over ≤21 days of weigh-ins (null under 2 points /
  3 days span); `pace_status` is `'on'|'behind'|'fast'|null` where `'fast'` = losing >~1%
  bodyweight/wk; `week_sets` counts ALL sets incl. timed, tonnage still excludes them.

### Body, nutrition, capture

- Bodyweight log (`logWeight`/`listWeight`, syncs `profile.weight_lb`); the TDEE + lean-safe goal
  feasibility math (`computeGoalCheck`); free-text activity parsing (`parseActivity`).
- Meal plans: `getMealPlan`/`updateMealPlanDays` (replaces `parsed.days` for reorder/edit while
  PRESERVING all other parsed keys like `daily_kcal`/`shopping`; meals are coerced/clamped — kcal
  0–3000, macros 0–500, strings capped). `swapMealInPlan` replaces one meal in
  `parsed.days[day].meals[idx]`, returns `{plan, meal}` or null, and drops any cached `recipe` on
  purpose (new meal → new recipe), while `updateMealPlanDays` carries a valid `recipe` through
  reorders/edits. `setMealRecipe` caches an agent-written recipe under
  `parsed.days[day].meals[idx].recipe` (coerced/clamped: summary ≤400, time_min 0–240, servings 1–8,
  ≤20 ingredients, ≤15 steps, ≤6 tips; null when plan/day/meal missing or no steps AND no ingredients
  survive), returns `{plan, recipe}` or null. Day matched case-insensitively; all other parsed keys
  preserved.
- Adaptive nutrition: `estimateExpenditure(windowDays=21)` → MacroFactor-style `{tdee, confidence,
  points, intake_avg_kcal, trend_lb_wk}` — TDEE ≈ avg intake − recency-weighted weekly weight
  trend×3500/7. Adherence-neutral (a thin week only lowers confidence, never blames), suppressed
  during an active trip/illness window.
- Effortless capture: `frequentFoods(hour?)` → recent distinct foods near a time-of-day band, with
  carried-through macros for one-tap re-log. `setSessionFeedback(date, {soreness, performance,
  joint_pain})` writes the 1-tap autoregulation feedback the coach reads to bend volume.
- Check-ins (`addCheckin`/`getCheckinByDate`/`listCheckins`); food notes.

### Day intelligence & recovery

- `dayRead(date?, recovery?, unifiedState?, underfuelingSnapshot?)` → a deterministic
  `{kind:'train'|'easy'|'rest'|'done', focus, why, est_minutes, signals}` read, decided by the first
  rule to fire, in order (`src/repo/brain/day-read-rules.ts` carries the words, `src/repo/day-read.ts`
  carries the order): already-logged loading work → `done`; a fresh short night corroborated by a
  short rolling sleep average → `rest`; the unified signal state's protect posture → `rest`/`easy`,
  voiced through `action.voice` — the athlete-facing register — never the machine-facing `action.reason`
  it stands beside; stacked loading days (≥3, outside an active recovery week), a recovery-dose
  overrun, a low check-in, or low readiness → `rest`; already-logged light work, or a running-volume
  spike while loading → `easy`; a plan day is due → `train` (carrying caveats, including a
  chronic-short-sleep one); a chronic-but-not-acute short-sleep pattern with nothing due → `easy`;
  otherwise `easy` ("nothing programmed"). Any fresh, non-stale evidence in the `health_constraints`
  dimension — an active injury, but equally an illness or any other item that dimension carries —
  adds its own caveat to every rest/easy read regardless of which rule fired, named in the athlete's
  own register through the same voice mechanism rather than splicing a machine-facing evidence line
  behind a fixed lead-in. The guard follows the DIMENSION rather than one field name
  (`field === "active_injury"`) precisely so an illness is never silently dropped from a continuity
  escalation an injury would otherwise have triggered. The agentic sentence layers on top via
  `buildDayReadPrompt`. **Parameter contract** (documented on the signature itself): every optional
  argument overrides exactly its OWN input and never narrows what the read may look at — `dayRead`
  always reads the training log, plan, activities, check-ins, context events and fuel state straight
  from the DB regardless of what a caller passes; `unifiedState` is the one parameter that scopes the
  whole signal state, and omitting it builds the state rich (see `dayPlanningSignalState` below).
- `getRecoverySummary(days, garminSummary?)` merges `garmin_daily_metrics` with the source-agnostic
  `daily_metrics`, preferring Garmin for sleep/HRV/RHR/body-battery. `recordDailyMetrics(source,
  date, metrics)` upserts one source's row (clamped at the trust boundary); `getDailyMetrics(source?,
  days)` reads them back.

**One rich signal state, shared by the Brief and the coach.** `dayPlanningSignalState(date,
provided?)` (`src/repo/day-read.ts`) is the ONE builder of `UnifiedSignalState` — memoized per
`(date, request)` under the same brain-snapshot key `getCoachContext()` already uses
(`brainSignal("signal_state:${date}", …)`) — and its nine `DayPlanningSignalInputs` are each optional:
a caller supplies what it already holds, and every input it omits falls back to its own producer,
probed individually behind try/catch so one thrower degrades that single input rather than the whole
read. Three of the nine — `trainingSignals` (joint pain, the low-performance flag) and `programState`
(an anticipated mesocycle reset), plus `expenditure` — carry `safety_override` constraints, and
"optional" used to mean a caller that omitted them silently built a WEAKER state with no error: the
Brief's own fallback path built its signal state from only the handful of inputs already in scope
inside `dayRead()`, while `coach.ts` built a separate, richer one for the coach prompt by calling
`planningSignalState` directly — so the Brief could say "train" on a day the coach context had already
gone `posture:"rest"` with `health_constraints` and `load_tolerance` both constrained. `coach.ts`'s
`getCoachContextFromSnapshot` now calls the same `dayPlanningSignalState` instead of a second local
build, so within one request the Brief, the coach context, the server-policy clamps and the persisted
`signals`/`input_fingerprint` all describe the SAME state — the rich/thin seam cannot reopen.
`programState` is keyed to the DATE BEING READ rather than to "now" (`program_state` for today,
`program_state:${date}` for any other date, since `getCoachContext()` only ever asks for today and
must stay on the shared key) — reading an earlier date used to get a mesocycle measured from today,
which could tell a day inside an applied recovery week that a reset was months overdue. Outside a
request scope (the scheduler's warm run has none) the memo is a pass-through, so a caller that must
agree with another instead threads the baseline explicitly: `computeDayRead` (`src/dayread.ts`)
computes its baseline once and now passes it into `buildDayReadPrompt(ctx, {…, baseline})`, which used
to recompute its OWN baseline from `context.signal_state` — closing the seam where the agent was shown
one state while `enforceDayReadSafetyPosture`/`enforceRecoveryWeekCadence` clamped, persisted and
fingerprinted a different one.

**One night is not a trend.** `SIGNAL_VOICE`'s sleep entries used to speak off `recovery.sleep_min` —
the latest DATED night, never an average — under a chronic-sounding key (`sleep_short`/`sleep_ok`), so
a single short night produced "short nights have been stacking up" directly above the Brief's own
signals row saying sleep was about normal. `sleep_night_short`/`sleep_night_ok`
(`src/repo/signal-state.ts`) now speak ONLY for that one dated night (singular-`night`-guarded
phrasing, so a variant that drifted into claiming a run of them fails its own `concept` regex); a
separate `sleep_trend` observation, voiced through `sleep_short`, exists only when `avg_sleep_min` (the
same multi-night average day-read's own `low_sleep` flag reads) sits under six hours, at `caution`
rather than a day-owning severity — a short average informs the day, it never owns it the way one
genuinely short night does. Readiness's `max_age_days` dropped from 3 to 1: the deterministic Brief
already refuses to let a reading older than a day force a recommendation, but at 3 days a stale
reading still reached the athlete through this layer, because the protect rule leads off
`action.posture` alone — a three-day-old subdued reading produced an easy read voiced as though it had
come in that morning. The word "fresh" is gone from the readiness sentences for the same reason (a
1-day-old reading is not this morning's). Older readings are not deleted; they resolve `stale`, which
is the same "context, never a gate" standing the prompt already gives them. The felt-energy
observation's machine-facing `summary` was rewritten out of second person and out of giving a verdict
— `"You're feeling run-down today — rest is the smart call."` is now `"The athlete reports feeling
run-down today."`, matching every sibling observation's third-person register (this string feeds the
prompt's posture line and the `based_on` provenance trail, not the athlete-facing voice, which is
unchanged). A `joinedCase()` helper also fixed a casing bug in the conductor's joined support/brake
sentence ("… supports the day. But …"): lowercasing the brake clause's first letter unconditionally
turned an acronym or device name into "hRV"/"apple"; it now lowercases only when the opening word owns
no case of its own.

**Which dimension is actually speaking.** `UnifiedSignalState.action.directives.training_source`
(`src/repo/signal-state.ts`) names the `SignalDimension` whose status produced `directives.training` —
`recovery_capacity`, `training_load_tolerance`, `health_constraints` or `energy_fueling` can each
independently produce `recover`/`modify`/`hold_aggression` via one ordered precedence chain
(`planningDirectives`'s `rungs`, most-constrained first, evaluated once so the verdict and its cause
can never drift apart); `null` only when `training` is `"proceed"`. `action.voice` speaks the day's
overall POSTURE, and on a ready/train day that posture is drawn from SUPPORT evidence — so a
`hold_aggression` day voiced only through `action.voice` told the athlete they slept fine and then
asked them to hold, naming nothing they were holding for. The Brief's hold-aggression lead
(`src/repo/day-read.ts`) now speaks `signalState.dimensions[training_source].voice` instead.
Deliberately NOT hashed by `dayReadInputFingerprint`, which selects `signal_action.directives` FIELD
BY FIELD (`training`/`fueling`/`schedule`) rather than spreading it whole: `training_source` picks
which voice narrates the lead, but every input that can actually MOVE it (recent load, check-in,
fatigue, logged-today, today's load) is already hashed elsewhere in the fingerprint, so the same
`hold_aggression` changing hands between two dimensions is not itself a new decision — hashing the
source too would discard a warm agentic read for pure churn.

**One directive, two unrelated causes.** `directives.schedule === "compress"` fires whenever the
`life_capacity` dimension sits at `watch`, and that can mean either a real dated commitment (the
CLOCK is the constraint) or `context.expect_worse_sleep` — a late night or a stressful stretch, which
squeezes RECOVERY and nothing else. Both observations write the same `field`, so the directive alone
can't tell them apart, and two independent copies of the discriminator (the Brief's caveat + its
60→40 `est_minutes` clamp in `day-read.ts`, and the conductor's compress card in `coaching-focus.ts`)
had drifted into two different answers. `lifeCapacityIsCommitment(state)`
(`src/repo/signal-state.ts`) is the one shared test now — it reads the arbitrated `life_capacity`
dimension's own `voice.key` (`"commitment_pressure"` vs `"schedule_pressure"`), never raw evidence,
because `dimensionState` always assigns a voice and a second path that can contradict arbitration
would be a competing arbitration rule, not a null-safety floor. Only a real commitment earns the
time-window caveat and the `est_minutes` clamp; the recovery-squeeze cause holds intensity for the
full session length instead of shortening it.

**The reading grammar binds the agent too.** `violatesReadingGrammar(text)`
(`src/repo/day-read.ts`) holds a sentence to the same four rules the deterministic vocabulary has
always been written to: no leaked engineering vocabulary (`deterministic`/`posture`/`baseline`/
`policy`/`fingerprint`/`directive`/`override`/`boundary`/any underscore), no device/clinical jargon
that has actually leaked into prose (`acute warning`, `readiness signal`), no numeric score/grade/
percent, and no gate language (`you must`, `do not train`, `forbidden`). `isValidDayReadAgentResult`
(`src/dayread.ts`) now runs the AGENT's `headline` and `why` through the same predicate before
accepting them — the sentence the athlete reads most mornings had been held to nothing, so a
compliant-shaped `{headline:"Readiness 38/100 — rest.", why:"…you must not train today."}` used to
validate and render verbatim. A violation is treated the same as any other shape failure: rejected,
so the fallback ladder can still land a compliant sentence, with the deterministic floor (which
passes this predicate by construction) as the worst case. `test/dayRead.test.js` runs every
registered deterministic phrasing through the predicate and asserts zero rejections, pinning the
zero-false-positive case for the shared rule.

**One `dayReadHeadline()`, not three.** The Brief's headline — the most prominent string on the card
— was the last piece of day-read prose still an unrotated literal, implemented three times: a
`deterministicHeadline` in `dayread.ts`, a byte-identical copy in the day-read use case, and a
hardcoded `"Take it easy."` inside the recovery-week softening clamp. `dayReadHeadline(read, date)`
(`src/repo/day-read.ts`) is now the one implementation, rotating `DAY_READ_HEADLINE_VARIANTS` by
calendar day like the rest of the vocabulary — date-keyed, never random, because the client compares
`headline` to decide whether to repaint, so a non-deterministic pick would repaint on every poll. A
`train` read with a known focus rotates the FRAME around the focus instead
(`TRAIN_FOCUS_HEADLINE`, e.g. "Lower body." / "Lower body today." / "Lower body is on today."), so the
focus itself still leads. `DAY_READ_POLICY_REASON_VARIANTS` also gained `agent_conservative_adjustment`
— the one athlete-facing server-policy reason that used to be a single hand-written literal inside
`computeDayRead`'s agent branch instead of read from the shared map like every other clamp reason.

**Rules carry their own words.** A `DayReadRule` (`src/repo/brain/day-read-rules.ts`) resolves to a
`{outcome, read}` pair where `outcome` is a `DayReadRuleOutcome` — a stable machine `code` for the
ledger *and* the athlete-facing `reasons` beside it. Before this round a rule was just `{name,
resolve}`, and `resolve()` built and returned the whole `DayRead` itself with one hardcoded `why`
literal baked into its body; `name` was documentation only (`resolveDayReadRule` never read it), so
no rule had any identity that survived past resolution and there was nothing for a ledger to key on.
Carrying a stable `code` on the outcome gives the ledger — and cross-day continuity's
`repeat_of_yesterday` check — something durable to compare, and `reasons` (a rotating set, not the
old single literal) is what actually varies the words day to day. A rule that reaches the athlete
without words is now a compile error.

**Prose varies across days, posture never does.** `reasons` is a *set* of phrasings of the same
judgement, because a stable input fires a stable rule: a chronic short sleeper or a lingering injury
hits the same branch every morning, and one literal per rule printed an identical sentence for weeks.
`pickDayVariant(variants, date, key)` (same module) rotates them — deterministic and offline (never
`Math.random()`, never wall-clock now), same day + same key ⇒ same text, consecutive days always
differ. Four vocabularies rotate through it: the outcome `reasons`, `DAY_READ_WHY_VARIANTS` (the
read's own `why`, keyed by rule code), `DAY_READ_POLICY_REASON_VARIANTS` (the server-policy clamp
reasons `dayread.ts` writes, keyed by the same rule code), and `SIGNAL_VOICE`
(`src/repo/signal-state.ts`, 38 keys / 114 phrasings) — the unified signal state's own athlete-facing
register, keyed by a small `voice` reference (`{key, subject?}`) an observation carries alongside its
machine-facing `summary` rather than sentences, so `UnifiedSignalState` stays cheap enough to keep
riding in every prompt payload. `UnifiedSignalState.action.voice` is always set — the athlete-facing
counterpart of `action.reason`, drawn from the same winning evidence — and degrades by posture, never
to `summary`, when that evidence carries no voice of its own. `DAY_READ_REQUIRED_CONCEPT` pins the one
idea each rule's words MUST carry whichever phrasing lands, so a new variant cannot drift away from
the meaning the rule exists to convey — a guarantee the old single-literal tests held only by
accident; each `SIGNAL_VOICE` entry carries its own `concept` regex beside its prose the same way.

The planned-training rule's own `why` is not one phrasing either: it is assembled from a lead plus a
run of lowercase, unpunctuated FRAGMENTS joined with `"; and "`, and the fragments used to be single
hardcoded strings even after the leads rotated — a chronic-short-sleep stretch or a recovery week read
the identical clause every morning. `DAY_READ_CAVEAT_VARIANTS` / `DAY_READ_CAVEAT_CONCEPT`
(`src/repo/day-read.ts`) register a rotating set for every fragment (recovery-week dose, an injury or
session-reported joint pain to work around, a generic "ease around", an anticipated deload, a running
volume spike, chronic low sleep, a hold on aggression, and the two schedule-compress causes above),
each with its OWN `pickDayVariant` rotation key so two caveats firing the same day rotate
independently rather than moving in lockstep. `clipText(value, max, opts)` (`src/repo/shared.ts`) is
the one truncation primitive behind what used to be seven independently reimplemented "trim to N
chars without cutting mid-word" helpers (`attention.ts`, `coaching-focus.ts`, `forward-timeline.ts`,
`learned-timeline.ts`, `team-week.ts`, `today-agenda.ts`, `training-milestones.ts`), each with its own
small, silent drift in ellipsis character, whitespace handling or boundary behavior; every caller's
`opts` reproduce its own prior exact output (`wordBoundary`/`sentenceBoundary` are opt-in — most of
the seven did NOT actually walk back to a word boundary despite the shared intent, so the default
preserves that pre-existing gap rather than fixing it as a drive-by; `team-week.ts` is the one caller
that opts into `sentenceBoundary` too). `selectionReason()` (`src/repo/plan-selection.ts`) is the one
machine→athlete caveat `day-read.ts` splices into the Brief's `why` when the adaptive plan-day picker
overrides the athlete's usual rotation day — second-person, lowercase, unpunctuated sentence fragments
(a lead clause, plus an optional "while …" avoid clause) rotated the same way, rather than the single
literal fallback it used to be.

The Brief is not the only reader of `SIGNAL_VOICE`. The coaching-focus **conductor** — the "Where to
focus" card on Stand's overview, Me → Health → Standing, and Progress → Program
(`src/repo/coaching-focus.ts`; Today suppresses only its day-posture lead there, as duplicate
narration once the Brief has printed it — other conductor threads still render on Today) — speaks
through the same `spokenSignalVoice(ref, date, key)` entry point (`src/repo/signal-state.ts`), on the
same `SIGNAL_VOICE_KEYS` (`protect`/`injury`/`fueling`/`schedule`) and the same
`UnifiedSignalState.date`, so one signal reads as one observation rather than two differently-worded
notes about the same morning a tab apart. `SignalDimensionState.voice` sits alongside each
dimension's `reason` for the conductor's parallel fueling/schedule cards, which speak to one
dimension rather than the day's whole posture.

**The work-around caveat is chosen by CAUSE, never by posture.** `modify` is reached from unrelated
causes — an active health constraint, an underfueling prescription, or the mixed-signal arbitration
tie-break — so keying the caveat off the posture alone produced injury-shaped prose ("work around IT
with pain-free substitutions") on fuel, HRV and sleep days, where "it" named nothing. `caveatCause(state)`
picks the most severe of `health_constraints` / `energy_fueling` / `recovery_capacity` /
`training_load_tolerance` / `life_capacity` (constrained beats watch, ties broken in that order) and
`CAVEAT_INSTRUCTIONS[cause]` supplies the instruction that follows the cause's own spoken sentence —
only the health instruction talks about substitutions; the others make sense with nothing to
substitute around. The caveat is also budgeted rather than clipped away: it carries the safety
instruction, so `joinCaveat()` appends it WHOLE and clips only the producer's own `why` to fit —
the old code clipped the JOINED string to 240 chars, which silently ate the instruction off the end
whenever the `why` ahead of it ran long. `CoachingFocus.caveat_cause` (and each `Candidate`'s own
`caveat_cause`) publishes the cause's plain-language label (`CAVEAT_CAUSE_LABEL`) alongside the text,
because two of the three paths that produce a caveat carry no other line it could be scraped from, and
the prompt layer used to hardcode the label as `"(injury/soreness)"` at both call sites — announcing
four of five causes to the model as an injury that did not exist. `src/prompt/shared.ts`'s
`caveatLine()` reads `caveat_cause` to render `EASE AROUND (<cause>): …` and falls back to the neutral
label only when a caller omits it.

**Cross-day continuity.** Nothing in the Brief used to read *yesterday's* Brief, so taking the
suggested rest never changed the input and the read never changed ("rest after rest after rest",
verbatim). `recentDayReads(date, limit)` reads back what was actually said from the rolling
`day_reads` cache, and `dayReadContinuity(date)` derives `{quiet_streak, yesterday,
repeat_of_yesterday}` — a missing day breaks the run (an unknown day is not a quiet day). Both
layers use it: the deterministic floor to vary its words and escalate a long quiet stretch (past
roughly two days it stops re-asserting its logic and offers the smallest thing worth doing — still a
suggestion, never a nag), and the agentic layer to know what it told the athlete yesterday. Only the
WORDS change; kind, focus and duration remain exactly as the rules decided.

**Fingerprint-aware invalidation.** `dayReadInputFingerprint(date, read, context)` answers exactly
one question: *could the decision have changed?* `readToday()` compares it against the cached row and
recomputes on a mismatch, so a warm agentic read is thrown away for the deterministic floor only when
something decision-relevant moved. Continuous measurements are reduced to the PREDICATES the rules
branch on (short sleep, low readiness, an anticipated deload, a volume spike) rather than hashed raw
— a mid-day watch sync used to flip the raw `avg_sleep_min` / `fatigue` blob and cost the athlete
their coach's sentence plus a fresh `brain_decisions` row for a read that never changed. Athlete-
entered context (check-ins, life events, plan selection) is kept whole because it only moves when the
athlete acts, and the signal state contributes its *action*, not its narration. Fuel deliberately
stays out: it has its own both-present serve-time comparator, which preserves cached rows written
before the visible fuel signal existed. When the cached row carries an athlete override,
`replaceStaleDayReadOverride()` does a compare-and-replace instead of a blind `saveDayRead` so a
steer cannot be silently clobbered.

**Invalidation has a write-path half too.** `invalidateDayRead(date?)` deletes the cached row
unconditionally, and that is still the right default: roughly 30 material-write sites across
`plan.ts`, `sessions.ts`, `nutrition.ts`, `health.ts`, `profile.ts`, `fueling.ts` and elsewhere call it
that way, for anything the athlete does deliberately or rarely (a logged set, a plan edit, a
check-in). `invalidateDayReadIfDecisionChanged(date?)` (`src/repo/day-read.ts`) is the write-path
counterpart to `readToday()`'s serve-time comparison above: it recomputes `dayRead()` and deletes the
cached row only when the fresh `input_fingerprint` differs from the cached one (a `curated` row is
left alone, matching the serve-time rule; a cold cache is a no-op, so the fresh-wake re-warm trigger
still fires normally). Reach for it instead of the unconditional form at a write site that is
HIGH-FREQUENCY telemetry rather than an athlete action — today that means three call sites:
`recordDailyMetrics()` (`src/repo/coach.ts:2348`, the source-agnostic daily-metrics upsert whose
unconditional delete was the original "rest after rest after rest" bug — a six-hourly watch sync
destroyed the warm read before any fingerprint was ever consulted), `upsertGarminDailyMetric()`
(`src/repo/activities.ts:1028`, the Garmin recovery sync that runs several times a day), and
`updateSessionGarminNarrative()` (`src/repo/activities.ts:1327`, a Garmin session-narrative patch that
`dayLoad` never reads, so a re-sync rewriting an identical blob used to nuke the Brief every time).
`updateDirective()` (`src/repo/coach.ts:1793`) is the deliberate exception in the other direction: a
directive status flip to resolved/dismissed stays unconditional even though it isn't a training write,
because directives sit outside the fingerprint entirely (`dayReadInputFingerprint` never hashes them,
so it could never move) while the Brief's prose is written against the active directive list — and
clearing a directive is a rare, explicit athlete action, not telemetry churn, so the unconditional
delete is correct there and switching it to the fingerprint-aware form would just leave a stale
directive voiced in the Brief.

### Person, memory, chat

- Memory CRUD (`addMemory`/`listMemory`/`updateMemory`/`deleteMemory` — `addMemory` dedupes exact
  repeats).
- Chat (`addChatMessage`/`listChatMessages`/`archiveChat`/`clearChat`/`saveDistilledMemories`):
  `listChatMessages` returns only the live conversation (`archived_at IS NULL`); `archiveChat` stamps
  every live row instead of deleting (clear/reset never hard-delete; archived turns stay in the DB
  and in exports); `saveDistilledMemories` persists an agent's distilled `{memories:[{content,kind}]}`
  — ≤12 items, content trimmed/capped at 300, kind clamped to a small allowlist, saved via
  `addMemory(content, kind, "chat-distill")`.
- Family roster (`addFamily`/`listFamily`/`getFamilyMember`/`updateFamily`/`deleteFamily`);
  life-context events (`addContextEvent`/`listContextEvents`/`updateContextEvent`/
  `deleteContextEvent` — trips/injuries/life events the coach plans around).
- `setProfile()` carries `about_me` (trimmed, capped 8000; `''` clears, `undefined` leaves intact).
- Settings/agent-selection (`getSettings`/`setSettings`/`getAgentConfig`/`pickAgentOrder`).
- Health documents (`addHealthDocument`/`listHealthDocuments`/`getHealthDocumentRaw` (incl.
  `file_path`, internal only) / `getHealthDocument` (public, strips `file_path`) /
  `updateHealthDocFields`/`deleteHealthDocument`).
- Full-DB export (`exportAll` / `snapshotDbTo`).

### `getCoachContext()`

Assembles the full snapshot fed to coaching agents: bounded `health` summaries + active/upcoming
`context_events`, plus `directives` (condensed cross-domain consequences), `recovery` (unified
Garmin+other view), `checkins`, `family`, `day_read` (so chat echoes the Brief) and `insights`
(recent visible reads). Additive by design — every existing consumer keeps working untouched.

Consumers get the whole snapshot; **prompts do not**. Serializing it into a `DATA:` block goes
through the per-site allowlist in `src/prompt/context-projection.ts` — so adding a key here does not
make it reach any prompt until that site lists it. See "The prompt-boundary context projection".

### Schema notes

`plan_items` has `warmup_sets` and `target_seconds` (the latter prescribes hold time for timed
exercises). `exercises` has `mode` (`'reps'` default | `'timed'`). `logged_sets` has `duration_sec`
(timed sets may have null weight/reps). `settings` has `onboarded`, `enrich_enabled`, `art_enabled`,
`art_enabled_at` (UTC stamp written by `setSettings` on every off→on flip of `art_enabled`; the
spend-telemetry window) and `meal_prefs` (free-text meal/schedule preferences — e.g. "I train fasted
most mornings" — embedded verbatim in the meal-plan and meal-swap prompts; trimmed, capped 2000).
`activities` and `food_notes` have `enrichment_status`. `chat_messages` has `archived_at` (set by
chat reset/clear, filtered out of `listChatMessages`). `sessions` has
`soreness`/`performance`/`joint_pain`. `profile` has `about_me`. `health_directives` has
`marker`/`uncertain`. `health_documents`, `context_events`, `checkins`, `daily_metrics`,
`family_members`, `health_directives` and `insights` are `CREATE TABLE IF NOT EXISTS` tables.

## The connected brain (markers → directives)

`prioritizeMarkers()` ranks the latest markers by an INTERNAL impact-score against evidence-anchored
`OPTIMAL_ZONES` — optimal-zone framing, NEVER a 0-100 grade — red-flagged first, then
furthest-from-optimal. `deriveDirectives()` is the deterministic engine that propagates each
off-optimal marker into per-domain `health_directives` via `MARKER_MAPPINGS`, idempotently clearing
and rewriting the `'markers'` source. `applyReviewDirectives()` does the same for an agent-emitted
review's directives under the `'health_review'` source. Both route through `reconcileDirectives()`, a
diff-based per-`directive_key` resolve: an unchanged existing row is kept untouched, a changed one is
updated in place, a row no longer desired is soft-resolved, and a new one is inserted — zero-churn
instead of clear-all-then-reinsert. `directivesForCoach()` condenses the active set for the prompt.
Plus `addDirective`/`getDirective`/`listActiveDirectives`/`listDirectives`/`updateDirective`.

Quiet insights: `addInsight`/`getInsight`/`listInsights`/`updateInsight`/`listVisibleInsights`
(new+seen only) /`recentInsightTexts`/`isDuplicateInsight` — the soft+real dedup guard so the same
connection is never surfaced twice.

### Marker grouping and display order

Markers are bucketed into meaningful health groups (`MARKER_GROUPS` in `propagation.ts`,
longest-match-wins on the name, same matcher shape as `matchOptimalZone`) so a comprehensive
Function-Health-style panel reads as ~20 clinical stories instead of one giant "Other Markers"
catch-all.

The `MARKER_GROUPS` **array order IS the display sequence**, and it is the **conventional clinical
lab-review order** a physician scans — NOT a longevity-impact ranking (that lives in
`prioritizeMarkers`'s per-marker sort + `healthFocus()`):

CBC (Iron & Red Blood, then White Cells & Platelets) → CMP (Metabolic & Glucose, Electrolytes,
Kidney, Liver & Pancreas) → Lipids & Cardiovascular → Inflammation → endocrine (Thyroid, Hormones) →
Vitamins & Minerals → the less-common specialty panels (Cardiac, Autoimmune & Antibodies, Cancer
Screening, Heavy Metals) → Urinalysis → the non-blood functional reads (Blood Pressure & Vitals,
Fitness & Metabolic Rate, Body Composition) → Other Markers (catch-all, always last).

Both the doctor export (`report.ts`) and the internal Markers catalog (front-end `07-me-health.js`)
render panels in this order so a value never sits where a clinician doesn't expect it. Within a
panel, markers are ordered the way that lab panel prints (e.g. electrolytes as Na/K/Cl/CO₂/anion
gap), via `MARKER_ORDER` (report) and `HEALTH_MARKER_ORDER` (front-end), which mirror each other.
Because matching is longest-match-wins, the array order is purely display sequence and never changes
which group a marker lands in.

A `<analyte> - Urine` dipstick name is forced to Urinalysis (the dash-suffix override, since the
serum key outranks "urine" — quantitative urine ACR reads "Random Urine", no dash).
`isNonClinicalMarker()` drops a non-analyte extraction at read time in `getMarkerHistory`
(non-destructively; the source doc stays): an eyeglass Rx (sphere/cylinder/lens-type from an eye-exam
doc); a generic document FIELD label an extractor leaks as a "marker" (`Result`/`Summary`/`Symptoms
Reported`/`Interpretation`/… — matched as the WHOLE name, so a real analyte merely containing the
word is unaffected; the canonical case is an Apple-Watch ECG export whose form fields became markers
and landed in Other); or a vendor composite/letter GRADE (`Body Score`, `Wellness Score` — the
constitution bans graded scores; `t-score`/`z-score` are exempt real body-comp analytes). Proper ECG
analytes (`ECG Rhythm`, QT/QRS/PR) group into Cardiac and a biological/metabolic-age read groups into
Fitness & Metabolic Rate.

Markers carry a deterministic `trend` (`{dir:'rising'|'falling'|'stable'|null, change, span_days,
n}` — stable when the net change is small vs the series' own spread). `getMarkerHistory()` and
`prioritizeMarkers()` both return `{ markers, groups }` (canonical-ordered `groups` present) with
per-marker `group`/`group_label`/`trend`. The review prompt surfaces each priority marker's group +
trend direction + reading recency so the coach speaks to trajectory ("rising over ~14 mo"), not just
the latest value. Reading recency renders human via `relAge()`/`absDate()` (see `docs/DESIGN.md`),
never a bare month-year.

## The Today lead arbitration (`src/domain/brain/today-attention.ts`)

Cairn already arbitrates the Today **rail** (`repo/today-agenda.ts`). What nothing arbitrated was the
**main column's lead**, because `briefHero()` hardcodes the Brief as the hero. So on a day whose read
is literally yesterday's conclusion reached by yesterday's rule — which the day-read layer now says
out loud via `signals.continuity` — the Brief still held the loudest slot while the genuinely new
thing (a finished session waiting on its one-tap read, a connection surfaced for the first time) sat
quietly beside it.

`decideTodayAttention(date, read)` returns `{primary, brief_state, items[]}`, where each item carries
an emphasis `tier` (`lead` / `supporting` / `quiet`) over the candidate surfaces `brief` | `feedback`
| `insight` | `weekly` | `fuel`. `briefState(read)` decides whether the Brief still has something new
to say, and is deliberately narrow: it yields ONLY on a quiet (rest/easy) day with nothing logged
whose own prose already admits it is repeating itself. A train day leads (there is a session to do), a
done day leads (the debrief is today's news), a steered read leads (the athlete just asked it
something), and a legacy cached row with no continuity block leads — absence degrades to today's
behavior, never to a demotion.

It runs inside `attachDayReadContext`, so every Brief response — REST, MCP and `agentJobs` alike —
agrees on what leads. It returns `null` for anything but the live local day (a routed past date
renders archival state and arbitrates nothing) and for any failure; the client renders a missing
`attention` exactly as it did before the field existed. Every probe is isolated, so a failing source
omits its own surface rather than the decision. The internal `RANK` numbers ORDER only and are never
serialized — the client receives semantic labels, the same rule as marker `impact_score`.

**Why this is separate from the rail agenda.** They answer different questions over different
surfaces with opposite contracts: `today-agenda.ts` budgets the RAIL and exists to REDUCE (cards
collapse behind one quiet "more", under a surprise budget across ~20 candidate producers), while this
arbitrates the main column's lead and can only ever reorder emphasis — it never hides a card, invents
one, or removes a way in. The agenda's "the Brief is ALWAYS the hero" is its rail contract; relaxing
it for the main column is precisely why this module exists. Do not merge them.

`ClientTodayAttention` in `src/contracts/client.ts` mirrors these types rather than importing them,
because that module is the client-facing contract and imports nothing outside `src/contracts/`.

## Prompt building (`src/prompt.ts`)

`buildCoachPrompt` embeds the full `getCoachContext()` snapshot and a strict JSON output contract,
plus non-negotiable training/nutrition guardrails — conservative load progression, injury
`constraint_note`s, lean-safe deficits.

`buildMealPlanPrompt` is framed as a longevity/getting-lean coach: a shared `LONGEVITY_GUARDRAILS`
block (protein anchor ~0.7–1 g/lb, 30g+ fiber, whole foods, oily fish 2–3×/wk, lean-safe only),
flexible meal-slot timing rules (no pre-workout meal for fasted morning training — substantial
post-training breakfast instead), the training split, and `settings.meal_prefs` verbatim.
`buildMealSwapPrompt({plan, day, mealIndex, hint})` drives the single-meal swap (replacement within
±10% kcal/protein unless the hint overrides; bare single-meal JSON contract).

Constitution-bound builders: `buildDayReadPrompt` (the Brief — reads the whole picture, honors an
athlete override, protects earned rest), `buildSessionPrompt` (on-demand session honoring
time/equipment/injury + the day read), `buildNutritionCheckinPrompt` (adherence-neutral adaptive
check-in over the derived expenditure — proposes a small ±100–250 kcal change only on genuine drift,
protein-first floors, `change:false` the common answer), `buildInsightPrompt` (ONE genuine
cross-domain connection or `{found:false}`, deduped against `recentInsightTexts`), and
`buildWeeklyReadPrompt` (a standing "how the week went + the one change" stored as a `weekly_read`
insight).

`buildDayReadPrompt` also takes an optional `baseline` (`opts.baseline`, threaded by `computeDayRead`
— see "One rich signal state" above) and carries a paired guardrail against overclaiming last night's
sleep: alongside the existing "no sleep data synced" guard, a ONE NIGHT IS NOT A TREND line tells the
agent that the `LAST NIGHT:` line is a single data point and forbids narrating it as a pattern ("short
nights have been stacking up") unless the SIGNALS block's `low_sleep` (the genuine multi-night average
flag) backs one — because a short night can sit under a normal multi-night average, which is exactly
the case where a "lately" sentence would contradict the signals.

`renderConnectedBrain(ctx, {domains})` folds the active cross-domain `directives` (filtered to the
relevant domain — nutrition for meals, training/watch for the coach/day-read) plus the unified
`recovery` view into a compact plain-language block, so a flagged lab already shapes meals and
training. Returns `""` when there's nothing to say.

`CONTEXT_GUARDRAILS` (shared across the coach/chat/meal prompts) covers the personal-context layer —
`health_documents` and `context_events` both feed `getCoachContext()`, and the coach is directed to
plan **around** them: travel-friendly/deload weeks over trip dates, de-load/swap exercises hitting an
injured area, dial volume back during flagged life events, factor health flags (e.g. low ferritin) —
explicitly framed as informational, not medical advice. It also covers FAMILY (plan around
commitments, let `about_me` personalize tone) and HEALTH DIRECTIVES (fold nutrition/training
directives in, respect `watch` items; an `uncertain`/uncited directive is a softer nudge).

`buildHealthReviewPrompt`'s `HEALTH_REVIEW_SCHEMA` emits a `directives[]` array (persisted via
`applyReviewDirectives`). `buildChatPrompt` adds a **PROGRESSIVE UNDERSTANDING** guardrail: when the
DATA shows an obvious gap (no `about_me`, an unknown training-time / food like-dislike) the agent MAY
ask ONE brief low-friction question and emit an `add_memory` action for the answer — never a
questionnaire.

### The prompt-boundary context projection (`src/prompt/context-projection.ts`)

Every plan-shaping prompt ends with a `DATA:` block, and for a long time that block was
`JSON.stringify(getCoachContext())` — the whole ~63-key snapshot, verbatim, at every site (~196 KB
per call on a demo seed, more on a real DB; for comparison the bounded coach-read TOOLS cap at
64–98 KB for an *entire* query loop). Most of it is dead weight at any given site: a meal or health
prompt never reads the run-zone table, and the composition prompt works strictly inside a decided
envelope and never reads the recovery blob.

This module is the ONE seam that fixes it: a declarative per-site key allowlist applied by a single
shared helper. `getCoachContext()` itself is untouched — every non-prompt consumer (MCP tools,
routes, `agentJobs`, the read-tool loop) still gets the full snapshot, and the builders keep reading
the full `ctx` for their own prose blocks (the `render*` helpers in `prompt/shared.ts`), so no
rendered guardrail changes. The trim happens only where the snapshot is *serialized into a prompt*.

Sites compose from cohesive **key bundles** (`PERSON`, `TRAINING_LOG`/`TRAINING_CORE`/`TRAINING_FULL`,
`ENDURANCE`, `FUEL`, `HEALTH_CORE`/`HEALTH_FULL`, `RECOVERY`, `BRAIN`) mirroring the per-domain slices
`getCoachContext()` is assembled from, so a prompt author picks domains rather than curating 60 key
names. A key earns its place at a site under a **three-part rule**: (1) the prompt's own text names
the key or names its domain as ground truth, OR (2) a `render*` helper invoked at that site reads it,
OR (3) the builder's own code reads it off the DATA the agent sees. Anything else is dropped — and
when in doubt, KEEP, because a wrongly-dropped key silently degrades coaching, which is far worse
than a large prompt. Each site's spec carries a comment naming what it drops and why.

Two within-key right-sizings apply on top: `recent_sessions` is capped per site (20 / 10 / 6) and each
logged set is **projected** to the fields a prompt actually reads (row ids and per-set `created_at`
cost ~20 KB of the 58 KB blob with nothing coaching-relevant in them) — projected, never
null-stripped, because `weight: null` means bodyweight and a missing key is a different fact from a
null one. And `compactRecovery` keeps ONE copy of the per-metric quality map that
`getRecoverySummary` emits up to four times (`quality`, nested `recovery.quality`, `coverage`,
`provenance`), a strict superset with zero information lost.

A third right-sizing is narrower and safety-motivated rather than size-motivated: `compactCoachingFocus`
strips `why` from a conductor item whose `day_posture` is set, on every site that carries
`coaching_focus`. A day-posture item's `why` is deliberately the Brief's OWN sentence, verbatim —
same voice, key and date (`src/repo/coaching-focus.ts`) — so one signal reads as one observation on
the athlete's screen. Handing that sentence to the agent as "the conductor's focus" is exactly the
parroting `day_read` is already dropped from every site to prevent; it had simply leaked back in
through `coaching_focus` instead. So a day-posture item keeps its `title`, `move` and `based_on` (the
machine-register evidence) and drops only the phrasing; `src/prompt/shared.ts`'s `renderCoachingFocus`
renders `based_on` as a `GROUNDS (evidence, not phrasing — say it in your own words): …` line in its
place, so nothing coaching-relevant is lost — the agent still has the raw signals blob and the
READINESS/LAST NIGHT lines to reach its own words from. A non-posture item keeps its `why` untouched,
since there it can carry the conductor's work-around caveat verbatim — a safety instruction, not
narration, and must not be dropped.

**Adding a prompt:** add a site to `PROMPT_CONTEXT_SITES`, point its `DATA:` block at
`promptData(ctx, "<site>")`, and extend `test/promptContextProjection.test.js`. Never go back to a
raw `JSON.stringify(ctx)`, and never trim by slicing a serialized string — that hands the agent
malformed JSON. Note also that adding a key to `getCoachContext()` does NOT make it reach any prompt
until the relevant sites list it.

## Chat turns (`src/chatTurns.ts`)

The durable, token-streaming chat-turn engine — the conversational counterpart to `enrich.ts`. Chat
is not a blocking request/response: `POST /api/chat` persists the user message + a `chat_turns` row
(status `queued`) and hands the id to this **serial in-process worker** (one CLI agent at a time),
returning immediately.

`runChatCompletion` runs the turn under an `AbortController`. The first agent in the (explicit or
rotation) order **STREAMS** if it's stream-capable (`runAgentStreaming` → emits live `delta` events on
the bus, sentinel-aware so the trailing actions JSON never reaches the bubble); any failure or a
non-streaming agent falls back to a **one-shot rotation**. Chat's success criterion is NON-EMPTY
TEXT, not parseable JSON, so it deliberately does NOT reuse the JSON-centric `runAgentWithFallback`.

The raw reply is split by `parseChatReply` into `{reply, actions}`; safe actions apply via the lifted
`applyChatActions({actions}, {agent, imagePath, message})` (`log_*`/`set_profile`/`*_memory`/
`add_context_event` apply now; `plan_update`/`plan_restructure` become DRAFT proposals), then the
assistant `chat_messages` row is written + linked.

Progress rides an **`EventEmitter` bus** (`onTurnEvent(id, cb)`) that the SSE endpoint forwards:
`phase` / `delta` (a live reply chunk) / `reset` (streaming fell back — clear the partial bubble) /
terminal `done`/`error`/`canceled`. `enqueueChatTurn`/`cancelTurn`/`recoverChatTurns` are the
lifecycle entries; `cancelTurn` flips state then SIGKILLs the live subprocess (a Stop — `agents.ts`
`runAgent`/`runAgentStreaming`/`runAgentWithFallback`/`runChosen` thread an `AbortSignal`). Degrades
like the rest of the loop (no agent → a calm error reply persists, nothing throws).

Because the turn lives in SQLite, a follow-up queued mid-think — or a turn interrupted by a tab
switch / reload / restart — survives: `recoverChatTurns()` (boot, alongside `recoverPendingEnrich`)
marks interrupted `running` turns `error` (their actions may have partially applied, so re-running
risks duplicates) with a calm thread note and re-enqueues `queued` ones.

REST surface: `GET /api/chat/turns/:id/stream` (SSE: a `snapshot` then `phase`/`done`/`error`/
`canceled`; reached with `?token=` under auth since EventSource can't set headers), `GET
/api/chat/turns` (active = queued+running, oldest-first), `GET /api/chat/turns/:id` (poll fallback),
`POST /api/chat/turns/:id/cancel`, `POST /api/chat/reset` (distill-to-memory, then archive).

## Agent execution profiles (`src/repo/settings.ts` + `src/agents.ts`)

*Which* agent runs an op is `TASK_POLICY`; *how* it runs is `TASK_EXECUTION_PROFILES`, its sibling in
`src/repo/settings.ts`, keyed by the same `taskForOp` class so the two policies read side by side.
Without it, effort was inherited from whatever the CLI's home settings happened to say — the same op
ran at a different depth on a dev box than on the deployed host. Every class is decided server-side:
daily reads and background structuring at `fast`/low–medium, composition and clinical-adjacent
reading at `deep`/medium–high, structural change and multi-specialist review at `deep`/`xhigh`.

Profiles are **provider-neutral**: an op asks for a model *class* (`fast` = the everyday read, `deep`
= the one worth paying for), and each `agents.json` entry maps the classes IT supports onto its own
CLI model name via `model_classes`. Nothing in `src/` names a concrete model, which is why an
Anthropic alias never reaches a non-Anthropic CLI; pin an **alias**, never a dated id, so a new
generation ships without a code change. A provider that declares no mapping (codex / antigravity /
grok) keeps its own configured model and takes only the effort.

Resolution chain, all pure and unit-testable offline: the declarative class →
`agent_profile_bindings[agent][task]` if the user set an override (migration v77, same JSON shape as
`chat_profile_bindings`, normalized by the shared generic `normalizeProfileBindings`) →
`resolveAgentProfileForClass`, which clamps to what that CLI actually declares. It never throws and
never invents a value: no model mapping, no `model_flag`, or no reasoning support simply omits that
field and the CLI runs on its own default (the offline `stub` always resolves to nothing, by
contract). `highestSupportedReasoning` degrades rather than fails — asking a three-level CLI for
`xhigh`/`max` lands on its own ceiling.

Resolution happens **once, at spawn time**, through `RunOpts.profile` — a resolver callback rather
than a direct import, because the policy lives in `repo/settings.ts` which imports `agents.ts`.
`runAgent` folds it in at the one chokepoint every spawn path passes through (direct call, the
`runAgentWithFallback` rotation, `runAgentStreaming`), resolving against the agent *actually chosen*,
so a rotation hands each provider its own model name and `runChosen` call sites need no per-site
wiring. An explicit `model`/`reasoning` always wins per field; a throwing or absent resolver is
simply no profile — a policy lookup must never break a coaching run.

**The timeout follows the effort.** A flat 90s interactive cap is right for a deliberately cheap op
but silently truncates a deliberately expensive one: the run is killed mid-think and the rotation
reads it as a failed agent. `interactiveTimeoutFor(reasoning)` scales the leash (low 90s → medium
150s → high 240s → xhigh/max `DEFAULT_TIMEOUT_MS`), reached via `interactiveTimeoutForOp(op)` for job
ops and `chatTurnTimeoutMs(profile)` for chat. `INTERACTIVE_TIMEOUT_MS` remains exported as the floor
of that ladder — do not pass it directly.

**Chat is deliberately absent from the table.** The adaptive chat router (`src/chatRouting.ts`)
already assigns a per-message lane profile and stays authoritative for model/effort; only the timeout
follows it, via the resolved profile rather than the task table. An op with no entry in the table
inherits nothing and behaves exactly as it did before the table existed.

## Headless token streaming (`src/agents.ts`)

`AgentDef.stream?: { format, args }` declares a CLI's NDJSON streaming mode. `runAgentStreaming`
spawns with those args, reads stdout LINE BY LINE, and maps each event to assistant text via
`streamDelta(format, line)` — a CONSERVATIVE per-CLI adapter (unknown shape → null, never garbage →
caller falls back). `agentSupportsStream(name)` gates the path.

Verified support:

| CLI | Streaming | Notes |
|---|---|---|
| Claude | yes | `-p --output-format stream-json --include-partial-messages`, true token deltas — verified live |
| Grok | yes | `--output-format streaming-json`, emits `{"type":"text","data":"…"}` text deltas + `{"type":"thought",…}` reasoning to skip — verified live on grok 0.2.54; the older xAI ACP `agent_message_chunk` shape is tolerated as a fallback |
| Codex | no | delivers its agent message only as a complete `item.completed` event (no token deltas) |
| Antigravity (`agy`) | no | no streaming flag |
| non-configured / `stub` | no | one-shot |

The **reply-marked chat contract** (`buildChatPrompt` + `CHAT_REPLY_SENTINEL`/`CHAT_ACTION_SENTINEL`
+ `parseChatReply`) is what makes streaming clean: the model writes a `===CAIRN_REPLY===` line, then
its athlete-facing reply as plain prose (streamed verbatim), then — only if it needs to act — a
`===CAIRN_ACTIONS===` line followed by `{"actions":[…]}`.

`parseChatReply` drops everything **before** the reply marker (autonomous agents like the
gemini/antigravity CLI narrate their tool steps as text first — "I will query the … table" — which
must never reach the bubble) and splits the actions on the action sentinel. The streaming `flush` in
`chatTurns.ts` is marker-aware: it withholds a forming sentinel at the tail and fires a `reset` to
wipe any pre-marker narration the moment the reply marker lands. A conservative
`stripLeadingNarration` safety net covers agents that ignore the marker — it drops only leading lines
carrying BOTH a step verb AND a filesystem/db token, so genuine coaching prose ("Let me explain your
zones", "I'll bump your squat") is never touched. Backward-compatible with a marker-less reply and
the legacy `{reply, actions}` JSON alike (`test/streaming.test.js`).

## Generated artwork (`src/art.ts`)

Photoreal/stylized images for foods, exercises and activities via Google's `gemini-3.1-flash-image`
(override with `GEMINI_IMAGE_MODEL`; needs `GEMINI_API_KEY`), cached in `data/art/` as
`sha1(kind:normalized text).png`. A strictly serial in-process queue (mirrors the `enrich.ts`
pattern: in-flight dedup by cache key, a throwing job never breaks the drain loop, plus an in-memory
negative cache so failed keys aren't retried until restart) generates on cache miss while `GET
/api/art` returns 204 immediately. It's a **direct REST call** (global fetch, 60s AbortController
timeout, atomic tmp-then-rename write) — NOT an `agents.json` CLI run. Degrades gracefully: no key /
`settings.art_enabled` off / known-failed → 204, nothing runs.

**Semantic cache layer.** Before any image call, `resolveConcept()` runs one cheap Gemini *text* call
(`GEMINI_TEXT_MODEL`, default `gemini-3.6-flash`, 20s timeout, temperature 0) asking whether the
query would render essentially the same picture as an existing `art_assets` row (comparison window:
150 most recent per kind; strict for exercise/activity — different movement/equipment is not a match;
lenient for food — same dish reworded is) and, if not, what canonical phrase to file the new image
under. The verdict persists in `art_aliases` (normalized query → asset key), so each unique phrase
pays at most one text call ever and `cachedArtPath`/`requestArt` resolve through aliases on every
later hit. Any canonicalize failure falls back to generating under the query's own key.

**Spend telemetry.** Every paid call (and every avoided generation) is recorded via
`repo.recordArtUsage` into `art_usage` — actions `generate` (flat `ART_IMAGE_COST_USD`, default
$0.039/image), `canonicalize` (token-priced via `usageMetadata` at
`ART_TEXT_IN_USD_PER_M`/`ART_TEXT_OUT_USD_PER_M`), `reuse` (carries `est_saved_usd`), `fail`.
Surfaced by `GET /api/art/stats` / MCP `get_art_stats` with a since-`art_enabled_at` window plus
all-time.

**Warming.** `warmArt()` pre-queues every image the PWA will ask for (exercise names; the current
non-discarded meal plan + draft's meals; ~30 recent food notes; distinct recent activity types via a
duplicated `ACT_ART_PHRASE` map that MUST stay in sync with the client) — queries are built exactly
like the PWA's (`.trim().slice(0,120)`) so cache keys match. It runs ~5s after boot in `server.ts`
and on `POST /api/art/warm`, returning `{queued, skipped}`. `data/art/` is a regenerable cache (safe
to exclude from backups).

**Offline seed-art pack.** `seed-art/` — pre-baked, ffmpeg-downscaled images keyed by the SAME
`cacheKey` as the live cache, plus a `manifest.json` — ships in the repo so a fresh seed / the demo
renders real studio photos with NO key at runtime. `installSeedArt()` copies the files matching THIS
DB's `enumeratePwaArt()` queries into `data/art/` (idempotent — never clobbers a real image, no-op
when the pack is absent in a slim checkout), wired into `seedIfEmpty()` (`seed.ts`) and the demo CLI
(`demoSeed.ts`, exporting `seedDemo()`). Rebuild it rarely (after changing demo content / art style)
with `npm run seed:art:build` (`src/buildSeedArt.ts` — needs a Gemini key + ffmpeg; seeds the demo
into a THROWAWAY DB, `pregenerate`s each image under its DIRECT cache key bypassing semantic-dedup so
the pack is alias-free, downscales to a small JPEG, writes the pack + manifest, prunes orphans). The
`GET /api/art` route sniffs the magic bytes (`0xFF 0xD8` → `image/jpeg`) so a JPEG-in-`.png` pack
file serves with the honest type under `nosniff`.

## The scheduler (`src/scheduler.ts`)

The optional proactive coaching cadence: a 60s `setInterval` reads `settings` each tick (so the
schedule is toggleable live) and, when `coach_enabled` and the configured `coach_day`/`coach_hour`
match, creates one weekly proposal via the auto rotation and routes it through the shared autonomy
policy. First-run settings seed from the legacy `COACH_AGENT`/`COACH_DAY`/`COACH_HOUR` env vars.

The proactive tick (gated on `proactive_enabled`) also creates a **continuous plan-evolution**
proposal on two cadences: the WEEKLY slot (calendar), and a **data-triggered** EARLY proposal when
the athlete's logged training has materially shifted (`repo.programEvolutionTrigger()` — a lift
plateaued/regressing and wanting a variation, a muscle group under its productive volume range, or a
cadenced re-test due). The trigger is checked ≤1×/day, fires only on a NEW condition `signature` (a
standing weak point acts once, never daily) with a ≥5-day cooldown, skips the tick where the weekly
slot is already running, and shares the weekly proposal's single-slot dedup
(`AUTO_EVOLUTION_INSTRUCTION` + `supersedeAutoEvolutionDrafts`, coordinated via `app_state`
`program_evolution_trigger_sig`/`_last_draft_date`) so it never piles up. `evolveProgram(agent,
instruction, hooks, { task })` focuses the agent on the trigger reasons WITHOUT changing the stored
dedup key.

The scheduler also drives the whole-person trajectory's monthly / phase-boundary /
unexplained-regression revision conferences.

## Background enrichment (`src/enrich.ts`)

Free-text activity logs and food notes save **instantly** via the offline regex parser
(`parseActivity`), then — if `settings.enrich_enabled` (default on) and an agent is reachable — a
**background, in-process serial queue** runs `buildEnrichPrompt()` through `runAgentWithFallback()`
to (a) refine the entry's structured fields and (b) distill genuinely-notable durable facts into the
`memory` table. Uploaded health documents are the third kind: the job hands the agent the **absolute
file path** (`buildHealthEnrichPrompt`) — the CLIs can open local files — to extract markers + a
summary + memory.

- **Kinds**: `'activity' | 'food' | 'health'` (plus `'garmin_strength'`). **Status machine** on
  `activities`/`food_notes`/`health_documents` `.enrichment_status`: `pending` → `in_progress` (set
  *before* the agent `await`, so a crash leaves a recoverable marker) → `done`/`failed`/`skipped` (or
  `null` = not applicable). `recoverPendingEnrich()` (called from `server.ts` at boot) re-enqueues
  `pending`+`in_progress` rows for all three kinds.
- The queue is **strictly serial** (one CLI subprocess at a time), uses a shorter 120s timeout than
  the coach loop, and a throwing job never escapes the drain loop. A health job refuses a
  non-absolute `file_path` (skips) — that's the only thing constraining the agent's file read to
  uploads.
- Agent-provided fields are **type-coerced and clamped** before write; `memory` items are added via
  `addMemory` (which dedupes exact repeats). Prompt-only dedup is a soft hint, so the code-level
  dedup is the real guard.
- The frontend watches the status flip over **SSE** (`GET /api/activities/:id/stream` /
  `/food-notes/:id/stream` / `/health-docs/:id/stream` — fed by the status-transition bus in
  `src/enrichBus.ts`, emitted from the repo status setters) and upgrades the entry in place, falling
  back to polling `GET .../:id` when EventSource fails.
- Degrades gracefully end-to-end: disabled / no agent → `skipped` (written directly at insert, no
  queue churn); a failure or wrong-shape (e.g. coach-proposal) response → `failed`/no-op with the
  regex parse (or the as-uploaded doc) left intact.

### Health ingestion is completeness-first

A modern panel like Function Health lists 100+ markers; a weaker model used to curate that down to
"the interesting ones". Three deterministic guards make it transcribe EVERY marker:

1. The health job picks `repo.pickHealthAgentOrder()` — Claude-first, then Codex, then the rest, NO
   round-robin cursor side effect, an explicit `agent_routes.health` pin still wins — instead of the
   load-spreading rotation, because faithful transcription matters more than spreading load.
2. `buildHealthIngestPrompt` carries a hard "transcribe every marker verbatim, do not curate, include
   the in-range/normal long tail (full CBC differential, electrolytes, the whole urinalysis, omega
   sub-fractions, every hormone, blood type)" contract + a self-reported per-panel `marker_count`.
   (The old prompt literally said "prefer real, decision-useful markers" — that was the curation bug.)
3. For a **pasted-text** source (`text/plain`) the job estimates the source's marker count with
   `repo.estimateMarkerCandidates(text)` (counts value lines, excludes section headers + flag words)
   and, if the extraction is grossly short (`< 80%` of an estimate ≥ 40), re-runs ONCE Claude-first
   with an `emphasizeCompleteness` nudge and keeps whichever attempt captured more.

The per-panel cap is `repo.MAX_MARKERS_PER_PANEL` (250). The chat `log_health` action carries the
same "no curation" instruction and points big pastes at the Health tab's paste box.

## PWA surfaces (`public/`, source in `src/client/**`)

Dependency-free vanilla JS. The tabbed client talks only to `/api/*` and lives in `public/js/*.js` —
~150 small ordered modules (the numbered `01-core` … `10-boot` shell files plus ~140
`*-client.js`/`*-controller.js` slices), each an IIFE that **shares one global scope** (no bundler
dep; load order matters — so a top-level eager cross-module reference must use a lazy `() => fn()`
thunk, since function hoisting does NOT cross `<script>` boundaries; see
`ME_HANDLERS`/`PROGRESS_HANDLERS`).

`scripts/build-client.mjs` concatenates those modules, in the exact canonical order, into a handful
of ordered `public/js/bundle-*.js` bundles (the `BUNDLES` manifest is the source of truth for that
order); `index.html` loads just those bundles (`/art.js` still first) while `sw.js` precaches them.
`10-boot.js` is a 2-line shim (`startAppShell()`) — the boot sequence lives in
`src/client/app/startup.ts`. `sw.js` `skipWaiting()`s on install and the client reloads once on
`controllerchange` (`src/client/app/service-worker.ts`, guarded against the first-ever install), so a
deploy goes live on the next open.

### Illustration libraries

`public/art.js` is the **CairnArt SVG illustration library** (plain script loaded before the `js/`

interpolated into the SVG, so its output is inserted into `innerHTML` raw. The client wraps every

plain-script/`window.`-global/precache-before-bundles pattern, vendored from the "Body

`src/client/cairn-body-figure.ts`): one authored anatomical drawing (viewBox `0 0 260 640`,
male/female from a shared skeleton via a per-zone x-warp) exposing `figureSvg(side, tones, opts)` +
lower-level `silhouette`/`muscles`/`CALLOUTS`/`GLOWS`/`waistTrace`, plus the tape-driven measured
model (`referenceTape`/`widthScales`/`measuredSilhouette`/`measuredPoint` — real circumferences
re-proportion each body zone against a height-derived reference physique; references, never
mandates). It drives **Train › Muscle balance** (`progress-overview-client.ts` `tovFigureSvg` →

drawn over the dashed reference ghost, tappable measurement callouts, a selected-site detail panel +

reached via file-local guarded accessors (mirroring `art()`) so a missing lib degrades to the
ellipse-pack / tape-driven-croquis fallbacks.

**Chat** is a dynamic, non-blocking, token-streaming surface: the composer never locks, so a
follow-up typed while the coach is thinking just **queues** (rendered as a "Queued" bubble); a single
`EventSource` streams the oldest active turn (`chatMonitorEnsure`/`chatOpenStream`, finalizing each
bubble **in place** so order holds with several queued), advancing to the next as each finishes. When
the chosen agent streams, the reply renders token by token — a `delta` event appends to a live
`.stream-text` span with a blinking `.stream-caret` (`appendStreamDelta`/`ensureStreamingBubble`),
then `finalizeTurn` swaps in the full markdown; a `reset` event reverts to the calm "Thinking…" dots.

mirrored to `localStorage` (`saveChatDraft`/`loadChatDraft`) and the in-flight + queued thread is
rebuilt from `/api/chat/turns` (`chatReconnect`) on every render. The monitor tears down when leaving
the Chat tab (`chatTeardownMonitor` in `switchTab`/`activateTab`). Messages group under day dividers
with older days collapsed behind "Show earlier"; starter chips show when the conversation is empty;
the header "fresh start" button hits `POST /api/chat/reset`. Enrichment polling guards against
stale-tab writes via a `pollToken` bumped on every (re-)render.
